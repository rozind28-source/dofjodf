Все баги ниже найдены при разработке и **подтверждены реальными числами с бирж**,
а не выдуманы постфактум. На каждый в `tests/` есть регрессионный тест.

- **Раунд 1** — исходная разработка: баги 1–11
- **Раунд 2** — графики и биржи MEXC / Gate / Aster / Hyperliquid: баги 12–25
  (замеры по биржам — в [`EXCHANGES.md`](EXCHANGES.md))
- **Раунд 3** — «пустая сетка в LIVE», drawer и `[hidden]`: баги 26–32
- **Раунд 4** — фокус-режим (одна биржа + один рынок + top-N по фильтру): баги 33–38

## 1. Инверсные контракты: плотности в триллион долларов

**Симптом.** В разделе «Плотности» у Bybit BTC стоял уровень объёмом
`$1 009 818 318 229`. Реальная сумма всех 200 уровней стакана — `$12 586 030`.
Расхождение в ~80 000 раз ≈ курс BTC.

**Причина.** У инверсных (coin-margined) контрактов вроде `BTC/USD:BTC` размер
позиции номинирован в USD, а не в монете. Код считал стоимость уровня как
`price · amount`, хотя `amount` уже был в долларах → получался `price²·amount`.

**Доказательство** (живой API Bybit):
```
BTC/USD:BTC  inverse=True  contractSize=1.0
  trade: amount=500.0  price=83759.3  cost=0.0059694 BTC
  → amount·price = $41 879 650   (абсурд: сделка на 500 контрактов = $500)
```

**Фикс.** Единый метод `SymbolState.quote_value()`, знающий тип контракта:
```python
if self.inverse:
    return amount * contract_size          # контракты уже в USD
return amount * contract_size * price      # линейные/спот
```
Применён во всех трёх местах, где объём переводится в деньги: сделки (дельта/CVD),
стакан (дисбаланс) и кластеризация плотностей.

**Регрессия:** `test_quote_value_inverse_vs_linear`, `test_inverse_volume_not_multiplied_by_price`.

## 2. USD-оборот: у каждой биржи он лежит в своём поле

**Симптом.** OKX `BTC/USD:BTC` показывал объём `$0`, хотя реальный оборот ~$582M.

**Причина.** Поля `baseVolume`/`quoteVolume` в ccxt значат разное в зависимости
от типа контракта, а для OKX `quoteVolume` вообще `None`:

| Рынок | `baseVolume` | `quoteVolume` |
|---|---|---|
| Bybit linear | 75 922 BTC | 6 386 753 044 USD ✅ |
| Bybit inverse | 224 364 679 USD | 2 663 BTC ⚠️ |
| OKX linear | 9 735 576 контрактов | `None` ⚠️ |
| OKX inverse | 5 825 120 контрактов | `None` ⚠️ |

**Фикс.** `compute_usd_volume()` с явным порядком правил: инверс → `base·contractSize`;
иначе `quoteVolume` (с поправкой на валюту котировки); иначе `base·contractSize·price`.

**Сверка с независимым источником** (raw-поля биржи):
```
Bybit inverse: turnover24h = 2663.47 BTC · $83 759 = $223M  ≈ baseVolume $224M ✅
OKX   inverse: volCcy24h   = 6925.85 BTC · $83 776 = $580M  ≈ base·cs   $582M ✅
OKX   linear:  volCcy24h   = 97 355 BTC  · $83 830 = $8.16B ≈ base·cs·p $8.16B ✅
```

**Регрессия:** `test_usd_volume_real_cases` (4 параметризованных случая с живыми числами).

## 3. `ret(3600)` возвращал 15-минутную доходность под видом часовой

**Симптом.** Не видно снаружи — колонки «1ч» и «4ч» просто показывали неправильные числа.

**Причина.** Буфер истории цен — deque на 900 точек (~15 минут). `ret(seconds)`
искал первую точку старше `now − seconds`; если история короче окна, такой точки
нет, и возвращалась **самая старая из имеющихся**, то есть доходность за 15 минут.

**Фикс.** Явная проверка покрытия окна:
```python
if newest - oldest < seconds * 0.9:
    return None
```
Теперь `ret()` честно возвращает `None`, а `to_row()` переходит на запасной путь —
доходность по 1m-свечам (`ret_ohlcv`), которые покрывают до 6.6 часа.

Это самый опасный баг из всех: данные выглядели правдоподобно, но были неверными,
и по ним срабатывали бы алерты.

**Регрессия:** `test_ret_returns_none_when_history_shorter_than_window`,
`test_ret_falls_back_to_ohlcv`, `test_multi_tf_values_are_distinct`.

## 4. Кластеризация стакана сливала все 200 уровней в одну «плотность»

**Симптом.** `заявок=49`, объём = сумма половины стакана.

**Причина.** Допуск кластеризации задавался в процентах от цены: `0.05%` от
$83 813 = **$42**. Тик Bybit по BTC — $0.1, то есть весь стакан из 200 уровней
умещается в $20 и гарантированно попадает в один кластер. Для дешёвого альта
тот же процент, наоборот, вырождается в один тик.

**Фикс.** Допуск зажат между 1.5 и 40 тиками:
```python
tol = min(max(ref * cluster_pct / 100.0, tick * 1.5), tick * 40)
```

**Доказательство** (живой стакан Bybit BTC):
```
cluster_pct=0.05% → tol=$41.9 → в один кластер сливается 200 уровней из 200
cluster_pct=0.01% → tol=$8.4  → 28 уровней
после фикса       → 10 кластеров по ~40 уровней, топ = $3.35M при стакане $16.7M
```

**Регрессия:** `test_book_clustering_does_not_merge_whole_book`.

## 5. Спайки вида «723205x» в первые минуты работы

**Симптом.** `BTC/USD:BTC spike ratio=723205.84` через 86 секунд после старта.

**Причина.** Две наложившиеся ошибки:
1. База для сравнения бралась как «суточный объём / 1440», то есть в других
   единицах и без учёта размера контракта (см. баги 1–2).
2. Сравнение шло с первой же минуты, пока настоящих закрытых минут ещё нет.

**Фикс.** База считается **только** как медиана уже закрытых минут, измеренных
тем же способом, что и текущая; первые 3 минуты детектор молчит; добавлена
верхняя граница `ratio < 1000`, отсекающая мусор в данных.

**Регрессия:** `test_no_spikes_before_three_minutes`, `test_spike_ratio_capped`.

## 6. Binance отклонял `depth=200` — стаканов не было вовсе

**Симптом.** В логе 25 ошибок, в разделе «Плотности» только Bybit и OKX.

**Причина.** У Binance USDM валидные значения глубины — `5/10/20/50/100/500/1000`:
```
BadRequest: binanceusdm {"code":-4021,"msg":"200 is not valid depth limit"}
```
Ошибка ловилась широким `except` и лишь инкрементила счётчик, поэтому снаружи
это выглядело как «на Binance нет плотностей».

**Фикс.** Пер-биржевой `book_limit` в `ExchangeConfig` (100 для Binance, 200 для
остальных) + логирование типа исключения в потоковых циклах, чтобы такие вещи
не прятались за счётчиком ошибок.

**Результат:** после фикса `errors: 25 → 1`, и Binance появился в топ-плотностях
(`BZ ask $9 040 818`, `SOL bid $2 892 448`).

## 7. `await` на синхронном клиенте — биржа не подключалась вообще

**Симптом.**
```
[Binance Futures] load_markets failed: object dict can't be used in 'await' expression
```

**Причина.** Для REST-вызовов создавался второй, синхронный клиент `ccxt.<id>`,

поэтому дублирующий экземпляр был не нужен (и вдвое расходовал лимиты).

## 8. Дубликаты ключей в replay-режиме

**Симптом.** Доходности за 5 минут вида `−76.7%` в демо.

**Причина.** Синтетический рынок генерировался циклом по `база × биржа` без
проверки уникальности: из 420 строк только 246 ключей были уникальны, 174 —
дубликаты. Один и тот же `SymbolState` засеивался дважды разными случайными
ценами, и история цен внутри него оказывалась от другого инструмента.

**Фикс.** Генерация по множеству уникальных комбинаций с явным `seen`, плюс
часть баз намеренно оставлена на одной бирже — иначе фильтр «независимые
инструменты» в демо невозможно было бы проверить.

## 9. Все таймфреймы показывали одно число

**Симптом.** `1м = 5м = 15м = 1ч = 4ч = −5.53`.

**Причина.** Следствие бага 3 плюс отсутствие истории на старте: все окна
смотрели в одну и ту же первую точку буфера.

**Фикс.** Два уровня: (а) `ret()` больше не врёт при короткой истории;
(б) в replay-режиме история и 1m-свечи синтезируются **до** старта, причём
свечи проходят через тот же `apply_ohlcv()`, что и живые данные, — демо проходит тот же код-путь, что и прод.

**Проверка после фикса:** все 5 таймфреймов различаются у 100% строк,
NATR считается из настоящих свечей, а не из случайного числа.

## 10. Гонка в WebSocket: первый батч уходил с дефолтными фильтрами

**Симптом.** Пойман тестом: клиент попросил `limit=10`, первый пакет пришёл со 150 строками.

**Причина.** `pusher` начинал слать данные сразу, не дожидаясь сообщения
`{type:"filters"}` от клиента. Пакет приходилось выбрасывать, а в UI на долю
секунды мелькала «не та» выборка.

**Фикс.** `pusher` ждёт `asyncio.Event`, который выставляет `reader` при получении
первых фильтров (с таймаутом 3 сек — чтобы клиент без фильтров тоже получил данные).

## 11. `trades24 = None` ронял replay при старте из живого снапшота

**Симптом.** `TypeError: unsupported operand type(s) for /: 'NoneType' and 'float'`
— пойман интеграционным тестом.

**Причина.** Bybit и OKX не отдают число сделок, поэтому `trades24` был переведён
в `Optional[int]`. Но replay-код делил его на 1440, предполагая `int`. Снапшот,
записанный из live-режима, содержит `"tr": null` для этих бирж → падение при старте.

**Фикс.** `(r.get("tr") or 1440)`, а инкремент числа сделок — только если оно не `None`.
Заодно `0` заменено на `None` в выдаче: ноль и «биржа не отдаёт метрику» — разные вещи,
и ноль ломал бы сортировку по числу сделок.

# Раунд 2: графики и новые биржи (MEXC, Gate, Aster, Hyperliquid)

Подробные замеры по биржам — в [`EXCHANGES.md`](EXCHANGES.md). Здесь только баги.

## 12. MEXC отдаёт уровни стакана тремя полями — стаканов не было вовсе

**Симптом.** 350 ошибок за минуту, MEXC отсутствовал в разделе «Плотности».

**Причина.** MEXC присылает `[price, amount, count]`:
```
bid[0] = [86608.0, 450512, 1.0]
```
У остальных бирж два поля. Жёсткая распаковка `for p, a in levels` падала с
`ValueError: too many values to unpack (expected 2)` — и в `apply_book()`, и
отдельно в `/api/symbol` (HTTP 500).

**Фикс.** Нормализация один раз в `SymbolState._norm_levels()`, и в `self.book`
складываются уже нормализованные пары — чтобы ни один потребитель не зависел от
формата конкретной биржи.

**Результат:** MEXC даёт 259 плотностей, топ $19.3M.

## 13. Коллизия id спот/своп — OI уезжал не в тот инструмент

**Симптом.** Gate BTC OI = `$0`, хотя bulk-эндпоинт честно вернул данные;
при этом 130 других символов Gate OI получили.

**Причина.** Один биржевой `id` бывает у двух рынков:

| Биржа | Коллизий |
|---|---|
| Gate | **526** (`OGN_USDT` → `OGN/USDT` и `OGN/USDT:USDT`) |
| Bybit | 292 |
| Aster | 40 |

`_to_ccxt_symbol()` сначала перебирал варианты вроде `raw.replace("_","/")` и
брал **первый найденный в `markets`** — для Gate это оказывался спотовый
`BTC/USDT`. Проверка `if symbol not in self.ex.markets` его пропускала, потому
что `markets` содержит оба рынка.

**Фикс.** Все ветки поиска фильтруются по `cfg.market`; `_build_id_map()` пишет
рынки чужого типа первыми, чтобы свой тип их перезаписал.

**Результат:** Gate BTC OI `$2 386 441 369` — совпадает с независимым расчётом
`position_size · quanto_multiplier · mark_price = $2.379B`.

## 14. Единицы объёма в OHLCV различаются даже внутри одной биржи

**Симптом.** Не видно снаружи: график рисуется, но объём врёт на порядки.
OKX показывал $75k/мин вместо ~$7M; Gate и MEXC — наоборот, завышали.

**Причина.** Замеры сырого объёма 1m-свечи против `baseVolume/1440`:

| Биржа | Рынок | ratio | Единицы |
|---|---|---|---|
| Gate | spot | 2.22 | базовая монета |
| Gate | **swap** | **17 407** | **контракты** |
| MEXC | spot | 1.92 | базовая монета |
| MEXC | swap | 1.36 | контракты (тикер MEXC тоже в контрактах — сравнивать не с чем) |
| OKX | swap | — | базовая монета: ccxt берёт `volumeIndex = 6` = `base volume` |

Для MEXC swap ratio ≈ 1 **обманчив**, поэтому единицы подтверждены независимой
сверкой: `volume24 · contractSize · price = $3.356B` против эталонного
`amount24 = $3.275B` (±2.5%).

**Фикс.** Флаг `ohlcv_vol_in_contracts` задан **на пару (биржа, рынок)**, а не на
биржу — спот Gate/MEXC пересчёта не требует. Нормализация двухступенчатая:
контракты → базовая монета → USD.

Первая версия фикса была неверной: флаг поставили на MEXC целиком, включая спот.
Поймал тест `test_exchange_config_flags`.

## 15. Gate: `contract_stats` не bulk и считает OI вдвое

**Симптом.** `HTTP Error 400: Bad Request` каждые 30 секунд.

**Причина.** Две ошибки сразу:
1. `/contract_stats` требует `contract=` → отвечает `400 MISSING_REQUIRED_PARAM`.
   Это точечный эндпоинт, а не bulk.
2. Даже с параметром его `open_interest` ровно **вдвое** больше
   `position_size · quanto_multiplier` — Gate считает обе стороны позиции:

| Контракт | `position_size · mult · mark` | `contract_stats.open_interest_usd` |
|---|---|---|
| BTC_USDT | $2 379 137 289 | $4 756 345 776 |
| ETH_USDT | $1 105 687 923 | $2 228 940 138 |

**Фикс.** Перешли на `/futures/usdt/contracts` — один запрос на все 1024
контракта, поле `position_size`. Это стандартная конвенция OI, как у
Binance/Bybit/OKX; иначе Gate выглядел бы вдвое крупнее остальных.

## 16. У Aster и MEXC ccxt не реализовал методы для OI

**Симптом.** Aster OI = 0/114 при полностью заполненном funding; MEXC — 0/486 по обеим метрикам.

**Причина.**
```
mexc  fetchOpenInterest=False  fetchFundingRates=False
aster fetchOpenInterest=False  fetchFundingRates=True
```
`_oi_targeted()` начинался с `if not self.ex.has.get("fetchOpenInterest"): return []`.

**Фикс.** Нативные эндпоинты:
- **Aster** — Binance-совместимый API: bulk funding через
  `fapi.asterdex.com/fapi/v1/premiumIndex` (767 контрактов), OI точечно через
  `/fapi/v1/openInterest?symbol=`
- **MEXC** — `/api/v1/contract/ticker` **без** `symbol` отдаёт все контракты с
  `holdVol`, `fundingRate` и `amount24` одним вызовом

**Результат:** Aster BTC OI `$481 638 898` (= 5580.5 BTC · $86 570, сверено с
прямым запросом), MEXC BTC OI `$4 997 257 109`, funding 100% на обеих.

## 17. `str.replace()` молча не применил патч

**Симптом.** Aster продолжал вызывать несуществующий `fetch_open_interest` и
сыпать 40 ошибок за цикл — уже после «применённого» фикса.

**Причина.** Патч искал текст, которого в файле уже не было (функцию переписали
ранее), а `str.replace()` при несовпадении не ошибается — он просто ничего не
делает. Код остался старым, а проверка была косвенной.

**Фикс.** Во все патч-скрипты добавлен `assert old in s` перед заменой. Теперь
несовпадение падает сразу, а не всплывает через несколько итераций.

## 18. В replay объём свечи рос в ~83 000 раз

**Симптом.** Пойман тестом `test_candles_volume_in_usd`: объём 1m-свечи
превышал суточный/1440 в 53 раза.

**Причина.** Две наложившиеся ошибки единиц:
1. `_roll_candle()` прибавлял к свече `inc` в валюте котировки, хотя объём в
   OHLCV хранится в базовой монете → расхождение ровно в цену BTC.
2. `_synth_candles()` брал объём из фиксированного `lognormvariate(6.0, 1.2)`,
   не привязанного к инструменту: у BTC и у ноунейм-альта гистограмма была
   одинаковой.

**Фикс.** `inc_base = inc / st.last`, а синтетический объём масштабируется
реальным оборотом инструмента и сразу приводится к базовой монете.

**Результат:** ratio «объём свечи / суточный÷1440» = 1.09–1.35 при математическом
ожидании `lognormal(0, 0.7)` = e^0.245 ≈ 1.28 — то есть единицы сошлись.

## 19. `EXCHANGES=gate` включал и Gate.io Spot

**Причина.** Отбор шёл по `id`, а он совпадает у спота и свопа → два коллектора
на одну биржу, вдвое больше подключений и лимитов.

**Фикс.** По `label` матчим всегда, по `id` — только первую подходящую

## 20. Автоматический выключатель на отказы биржи

**Симптом.** `errors` рос на сотни в минуту при полностью рабочих данных.

**Причина.** Gate стабильно отвечает `BadRequest` на подписку стакана по ряду
символов (`龙虾/USDT:USDT`, `SOXS/USDT:USDT`). Поток перезапускался каждые
2 секунды — бесконечно.

## 21. Память: история цен съедала 1075 МБ, процесс получал OOM-kill

**Симптом.** При подключении всех бирж RSS доходил до 759 МБ и процесс убивался
на ~105-й секунде.

**Причина — три независимых потребителя:**

| Что | Было | Стало |
|---|---|---|
| `price_hist` как `deque[tuple[float, float]]`, 900 точек × 6000 символов | 104 байта на точку → **1075 МБ** (вместе с двумя другими буферами) | `array('d')` → **69 МБ** |
| `quote_hist` | писался на каждой сделке и **никогда не читался** | удалён |
| `trades_hist` | не писался и не читался вовсе | удалён |
| кэш сделок ccxt (`tradesLimit=1000` на символ) | ~300 КБ × 400 символов ≈ **120 МБ** | `tradesLimit=200` |

Кортеж из двух float в CPython стоит 104 байта (tuple + два boxed float), тогда
как два `double` в массиве — 16 байт. Отсюда 13-кратная экономия.

**Новый `RingBuffer`** на `array('d')` хранит метки и значения в двух массивах,
подрезает их пачками (а не на каждый `append`, чтобы не делать memmove на всю
длину каждую секунду) и сохраняет интерфейс, который уже использовали вызывающие:
`len()`, итерация парами, `[0]`/`[-1]`, `.maxlen`.

**Важно про диагностику:** первый замер показал рост RSS на ~2.4 МБ/с, что
выглядело как классическая утечка. Контрольный замер с `gc.collect()` дал
дельты 19 → 11 → 7 МБ за 30 секунд — рост **замедлялся**, то есть это было
заполнение кэшей до их лимитов, а не утечка. Без этого замера можно было
начать искать несуществующий цикл ссылок.

**Результат:** тот же профиль (8 бирж) перестал падать и вышел на плато ~683 МБ;
лёгкий профиль (`TOP_N=25 BOOKS=10`) — ~660 МБ.

## 26. `start.ps1` без BOM — PowerShell 5.1 не смог разобрать файл

**Симптом** (реальный вывод у пользователя):
```
At ...\start.ps1:59 char:16
+ Write-Host "  2) Р”РРђР“РќРћРЎРўРРљРђ вЂ” РїСЂРѕРІРµСЂРёС‚СЊ, РїРѕС ...
+                ~
Unexpected token ')' in expression or statement.
Missing closing '}' in statement block or type definition.
```

**Причина.** Файл был сохранён в UTF-8 **без BOM**. Windows PowerShell 5.1
(штатный в Windows 10/11) читает `.ps1` без BOM как ANSI, то есть в русской
локали — cp1251. Байты кириллицы переинтерпретируются, и среди них оказываются
символы, ломающие лексер: в частности «ДИАГНОСТИКА» превращается в
последовательность, где встречается байт, отображаемый как `)`. Отсюда
`Unexpected token ')'` и рассыпавшийся `switch`.

Важно: **это не синтаксическая ошибка в скрипте**. Тот же файл в PowerShell 7
(который по умолчанию читает UTF-8) разбирается корректно. Локальная проверка
`node --check`-подобным способом невозможна — PowerShell в среде разработки не
был, поэтому дефект проявился только у пользователя.

**Фикс — два уровня:**

1. `start.ps1` перезаписан как UTF-8 **с BOM** (`EF BB BF`) + в начало добавлена
   установка `[Console]::OutputEncoding = UTF8`, чтобы русский вывод не ехал в
   консоли с другой кодовой страницей.
2. `start.bat` переведён на **чистый ASCII** (0 байт > 127). Причина та же по
   природе: `cmd.exe` читает `.bat` в активной кодовой странице, а не в UTF-8,
   поэтому любая кириллица там — лотерея. Теперь `.bat` работает на любой
   локали и любой политике выполнения, и является запасным путём, если `.ps1`
   снова не запустится.

**Заодно починено в `.bat`:**
- `!PROXY_URL!` использовался без `EnableDelayedExpansion` — внутри блока
  `(...)` переменные раскрываются на этапе разбора, то есть **до** `set /p`,
  поэтому введённый пользователем прокси туда не попадал. Ветка вынесена
  в отдельную метку `:proxy`.
- То же касалось `PORT`/`URL`: `set "URL=..."` стоял до ввода порта.
  Перенесено в `:run`.

**Регрессионная защита.** Добавлен `tests/test_encodings.py` (9 тестов), который
проверяет именно байты, а не текст:
- `start.ps1` начинается с `EF BB BF` и декодируется как UTF-8;
- в `start.ps1` нет признаков двойного перекодирования;
- `start.bat` содержит 0 не-ASCII байт и не имеет BOM (BOM в `.bat` ломает
  первую команду);
- в `start.bat` нет `!VAR!` без `EnableDelayedExpansion`;
- каждый `goto X` имеет метку `:X`;
- исходники Python и веб-ассеты валидны в UTF-8, в `index.html` есть
  `<meta charset>`.

Отдельная деталь: первая версия теста на мохибеку **упала на моём же
комментарии** — я привёл в нём искажённую строку как наглядный пример.
Литерал из комментария убран; тест остался строгим.

## 27. Контрольная точка диагностики давала ложный вердикт «интернета нет»

**Симптом** (реальный вывод у пользователя):
```
2. Контрольная точка (не крипта)
  [ OK ] DNS one.one.one.one → 1.0.0.1  (67 мс)
  [FAIL] HTTPS www.gstatic.com: URLError: <urlopen error [Errno 11001] getaddrinfo failed>

  → Интернет как таков недоступен (или заблокирован исходящий трафик).
```
При этом DNS очевидно работал — `one.one.one.one` резолвился за 67 мс.

**Причина.** Я выбрал **один** произвольный контрольный хост (`www.gstatic.com`)
и по его недоступности делал вывод обо всём интернете. Но `getaddrinfo failed`
(Windows: `WSAHOST_NOT_FOUND`, 11001) означает «имя не найдено», а не «сети нет».
При выборочной блокировке DNS один неудачно выбранный домен даёт полностью
неверный диагноз и уводит пользователя не туда: он начинает проверять кабель
и VPN, хотя нужно просто сменить DNS-сервер.

Отдельно: вывод «Интернет как таков недоступен» блокировал дальнейшие проверки
(скрипт спрашивал, продолжать ли), поэтому пользователь так и не увидел,
что именно не резолвится.

**Фикс — диагноз по трём независимым слоям вместо одного хоста.**

| Слой | Что проверяет | Зачем |
|---|---|---|
| a) TCP по IP-литералу | `1.1.1.1:443`, `8.8.8.8:443`, `104.16.0.1:443` | есть ли исходящий трафик **вообще**, DNS не участвует |
| b) системный DNS, нейтральные домены | `one.one.one.one`, `www.google.com`, `github.com`, `www.microsoft.com` | работает ли резолвер в принципе (4 хоста, а не один) |
| c) системный DNS, хосты бирж | все хосты из `PROBES` | блокируются ли **именно биржи** |
| d) прямой DNS-запрос к 1.1.1.1/8.8.8.8 | свой UDP-клиент в `app/netprobe.py` | кто виноват: локальная машина или вышестоящий DNS |

Слой (d) — ключевой. Системный `getaddrinfo` проходит через файл hosts, кэш
службы DNS и веб-экран антивируса; прямой UDP-запрос к публичному серверу — нет.
Их расхождение однозначно указывает на локальное вмешательство.

Матрица вердиктов (`ADVICE` в `doctor.py`):

| TCP | Нейтральный DNS | DNS бирж | Вердикт |
|---|---|---|---|
| FAIL | — | — | `no_network` — кабеля/файрвол/VPN |
| OK | FAIL | — | `dns_dead` — сменить DNS на 1.1.1.1 |
| OK | OK | FAIL | `exchange_dns_blocked` — выборочная блокировка бирж |
| OK | OK | частично | `partial_dns` — запускать, отключив недоступные |
| OK | OK | OK | `net_ok` — проблема выше DNS (геоблок, TLS, 443) |

Для `no_network` медленный обход бирж пропускается целиком: каждая висела бы
до таймаута, и пользователь ждал бы минуты ради заведомо известного ответа.

**Проверка.** Сценарий пользователя воспроизведён тестом
`test_verdict_exchange_dns_blocked`: подменяется системный резолвер так, что
нейтральные домены резолвятся, а биржевые — нет. Ожидается вердикт
`exchange_dns_blocked`, а не `no_network`.

**Побочно найденное.** В `_ver_tuple()` цифры pre-release-суффикса склеивались
с номером: `4.5.0rc1` → `(4, 5, 1)`, то есть release candidate считался **новее**
релиза 4.5.0. Проверка версии молча пропустила бы нестабильную сборку.
Исправлено: берутся только ведущие цифры каждой части.

## 28. Один транзиентный сбой DNS навсегда отключал биржу

**Симптом** (первый запуск у пользователя): все 8 бирж упали на `load_markets`
в течение двух секунд, скринер стартовал пустым. Повторный запуск диагностики
через некоторое время показал **полностью рабочую сеть** — все 8 бирж
подключились, `load_markets` прошёл у каждой.

То есть сбой был транзиентным. Но приложение этого не пережило: ретраев не было
вовсе, и биржа оставалась неподключённой до ручного перезапуска процесса.

**Вторая часть проблемы — таймаут.** Замер на машине пользователя:

| Биржа | `load_markets` | Рынков |
|---|---|---|
| gate | **18.9 c** | 6826 |
| hyperliquid | **16.1 c** | 823 |
| bybit | 3.9 c | 3659 |
| binance (spot) | 3.6 c | 4670 |

Дефолтный `timeout` в ccxt — **10 000 мс на запрос**, и коллектор его не
переопределял. `load_markets` делает несколько запросов, поэтому суммарно 19 c
не являются нарушением, но на медленном или нестабильном канале отдельный
запрос легко выходит за 10 c — и биржа отваливается.

**Фикс — три уровня:**

1. **Явный таймаут** `request_timeout = 20 000` мс (настраивается через
   `REQUEST_TIMEOUT`), с запасом поверх замеренных 19 c у Gate.
2. **Ретраи с нарастающей задержкой** (`load_retries = 3`, 2 c → 4 c → 8 c,
   потолок 20 c). Повторяются **только сетевые** ошибки: опционные
   (`fetchMarkets "swap" is not a supported market type`) от повтора не пройдут,
   поэтому их проброс наверх сохранён — иначе мы бы втрое дольше ждали
   заведомо безнадежный вариант.
3. **Цикл восстановления** `_revive_loop()`: если биржа так и не подключилась,
   коллектор не завершается, а каждые `revive_interval = 120` c пробует снова.
   Как только биржа ожила, поднимаются рабочие циклы — перезапуск процесса не
   нужен. Статус в API при этом `retrying`, а не зависший `error`.

Рабочие циклы вынесены в `_after_markets_loaded()`, чтобы их мог вызвать и
обычный старт, и восстановление (иначе логика запускалась бы в двух местах и
неизбежно разъехалась).

**Попутно:** при переносе в общий метод потерялось условие
`if settings.mode == "live"` вокруг дампа снапшота — в replay-режиме он
перезаписал бы боевой снимок рынка синтетикой. Условие возвращено.

**Ошибка, которую я допустил при правке и поймал тестами:** новые поля
(`request_timeout`, `load_retries`, `revive_interval`) были добавлены в
`ExchangeConfig` вместо `Settings`, а `ExchangeCollector.__init__` обращался к
`settings.request_timeout` → `AttributeError` на старте всех тестов. Закрыто
тестом `test_reliability_fields_are_on_settings_not_exchange`.

**Тесты:** `tests/test_resilience.py`, 11 штук — ретраи на сетевой ошибке,
отказ от ретрая на опционной, исчерпание попыток, `load_retries=1`,
переход в revive при неудаче, статус `retrying`, восстановление с поднятием
рабочих циклов, применение таймаута.

**Фикс.**

- Спот вынесен в `CORE_EXCHANGES` для Binance, Bybit, OKX, MEXC, Gate.io.
- Лейбл = **имя биржи без рынка** («Binance», «MEXC»); у биржи две конфигурации

  STORE строится по `id`, поэтому коллизий нет.
- В сайдбаре — сегментированный тумблер **«Фьючерсы / Спот»** с одним активным
  состоянием, применяется глобно ко всем разделам.
- Чипсы бирж, у которых нет выбранного рынка, гаснут (`disabled` + полупрозрачные)
  с подсказкой в `title`, чтобы клик не давал пустую таблицу.
- `EXCHANGES=mexc` теперь включает **оба** рынка биржи: дедупликация в конфиге
  шла по голому `id` и блокировала вторую конфигурацию. Ключ дедупликации
  заменён на пару `(id, рынок)` — гасятся только истинные дубли CORE/EXTRA.
- Добавлен `MARKETS=swap` для экономии памяти: спот-коллекторы не поднимаются.

**Проверено живьём:** `/api/grid?mt=spot` отдаёт MEXC Spot (`BTC/USDT`, 200 свечей),
`available_exchanges` для спота = `[Binance, MEXC]`, тумблер в UI переключает
выборку и перерисовывает сетку.

## 31. `[hidden]` не работал: drawer не закрывался, оверлей «загрузка свечей…» висел вечно

**Симптом** (со слов пользователя, подтверждено скриншотом): правая плашка
карточки инструмента **не закрывается**, хотя кнопка «закрыть ✕» есть и
кликается; в окне графика бесконечно видно «загрузка свечей…».

**Причина.** CSS-специфичность. UA-правило `[hidden] { display: none }` имеет
специфичность атрибута, а мои авторские правила — класса:

```css
.drawer      { display: flex; ... }   /* авторское */
.chart-state { display: grid; ... }   /* авторское */
[hidden]     { display: none; }       /* UA */
```

Авторский stylesheet выигрывает у UA, поэтому установка `el.hidden = true`
меняла атрибут, но **не визуальность**: элемент оставался `display:flex/grid`.
Drawer стоял поверх интерфейса, а оверлей загрузки — поверх canvas, закрывая
даже успешно отрисованный график.

**Почему тесты это пропустили.** Смоук-тест проверял `$("#drawer").hidden === true`
— то есть **атрибут**, а не видимость. Атрибут менялся корректно, тест был
зелёным при сломанном UI. Классическая ошибка «проверяем то, что удобно
проверить, а не то, что видит пользователь».

**Фикс.**

```css
[hidden]{display:none !important}
```

`!important` обязателен: без него `.drawer{display:flex}` всё ещё выше по
специфичности.

**Тесты переписаны** на проверку **вычисленного стиля**, а не атрибута:
`getComputedStyle(drawer).display === "none"` после клика по «закрыть» и после
Escape; то же для `.chart-state`. Плюс проверка, что оверлей не перекрывает
canvas после загрузки свечей.

## 32. При 10 000+ символов запросы свечей голодали: сетка и карточка «висели»

**Симптом.** В live-режиме с 10.5K инструментов сетка графиков пустая, карточка
вечно показывает «загрузка свечей…». В demo-режиме (где символов сотни) всё
рисовалось — отсюда впечатление «графики есть только в демо».

**Причина — две наложившиеся:**

1. `build_rows()` сериализует **все** символы в словари и вызывался на каждый
   WS-push (раз в секунду) и на каждый REST-запрос. На 10.5K символов это
   миллисекунды CPU в цикле, забивающие event loop; запрос `/api/grid` и
   `/api/candles` просто не получал времени исполниться.
2. У запросов свечей не было таймаутов ни на сервере, ни во фронтенде: медленная
   биржа (Gate ~19 c) или забитый event loop превращали их в вечно открытое
   соединение, а UI — в бесконечный спиннер без единой ошибки в консоли.

**Фикс.**

- **Кэш строк** в `api.build_rows(ttl=1.0)`: сериализация выполняется не чаще
  раза в секунду и переиспользуется всеми потребителями (WS-push, скринер,
  карта, grid). Период свежее периода push не нужен.
- **`asyncio.wait_for(..., 8 c)`** вокруг обращения к бирже за свечами
  (`_candles_with_timeout`): лучше отдать пустой ответ, чем держать соединение
  открытым. В ячейку добавлено поле `candles_ok`, чтобы фронтенд показывал
  «нет свечей (таймаут биржи)», а не пустой canvas.
- **`fetchT(url, ms)` во фронтенде** — fetch с `AbortController` и таймаутом
  (12 c для свечей, 15 c для сетки). По таймауту выводится понятное состояние
  с кнопкой «повторить», а не бесконечная «загрузка…». Заголовок сетки при сбое
  помечается «сервер не ответил».

## 33. Сетка графиков в LIVE собиралась 21 секунду (и это ещё не худший случай)

**Симптом.** Пользователь: «графики есть только в демо-режиме». В LIVE сетка
9 ячеек показывала «нет свечей (таймаут биржи)» или грузилась десятки секунд.

**Замер** (`tools/measure_focus.py`, 3 биржи × `TOP_N=150`, живые Binance/Bybit/MEXC):

```
ПОЛНЫЙ РЕЖИМ : hot=450, стаканов 90, лент сделок 360
               /api/grid 9 ячеек = 21.04 c   ← три прохода, медиана
ФОКУС top-50 : hot=50,  стаканов 30, лент сделок 50, прочие биржи paused
               /api/grid 9 ячеек =  0.13 c   ← в 160 раз быстрее
```

**Причина.** `/api/grid` брал ячейки из «топ по объёму среди всего, что попало
в хранилище», а не среди того, что реально стримится. Свечи для таких монет
заказывались у биржи по REST в момент запроса: 9 ячеек × последовательные
`fetch_ohlcv` с `asyncio.wait_for(8 c)` — и при занятом event loop часть ячеек
уходила в таймаут. Плюс WS-пуш раз в секунду сериализовал 2801 строку.

по текущему фильтру, перепроверка раз в 15 с. `/api/grid` в фокусе берёт ячейки
из текущего отбора (они гарантированно стримятся, а их свечи лежат в кэше
коллектора), WS-пуш сужается до того же набора, прочие биржи ставятся на паузу.

**Что важно:** таблица скринера и карта рынка при этом НЕ сжимаются — см. п.34.

**Регрессия:** `test_grid_uses_focus_selection`, `test_grid_without_focus_is_unchanged`,
живой замер `tools/measure_focus.py`.

## 34. «Сжать пуш» молча сжало и таблицу скринера до 50 строк

**Симптом.** После включения фокус-режима таблица скринера показывала ровно
столько строк, сколько монет в отборе: искать монеты стало негде, хотя тикеры
биржи мы и так получаем одним REST-запросом.

**Причина.** Таблица рисуется из WS-пуша, а пуш в фокусе сужен до отобранных
ключей (`restrict`). Одна и та же выборка обслуживала и «живые тики», и «полную
таблицу» — эти требования в фокус-режиме расходятся.

**Фикс.** Разделение каналов:

- клиент в фокус-режиме шлёт в сообщении `filters` флаг `base: true` и сам
  забирает полную вселенную через `GET /api/screener?ex=…&mt=…&limit=5000`
  (один запрос при смене фильтра/биржи/сортировки);
- сервер при `base=true` НЕ сужает пуш, но возвращает `meta.focus_count` —
  сколько монет реально стримится;
- фронтенд подмешивает живые тики в REST-базу по ключу (`mergeBase`), порядок
  строк при этом не меняется: инкрементальный рендер таблицы переиспользует
  DOM-узлы по позиции, и пересортировка каждую секунду пересоздавала бы все строки.

**Замер после фикса:** 778 строк Binance/swap в таблице при 50 монетах в стриме.

**Регрессия:** `test_screener_table_keeps_full_universe_in_focus`,
`test_ws_push_base_mode_keeps_full_universe`, смоук-проверка
«таблица скринера показывает всю биржу, а не только top-N».

## 36. Сигнал пробуждения ротации терялся: биржа минуту стримила старый набор

**Симптом.** Живой замер: через 10/20/50 секунд после выключения фокуса
у Binance оставалось `hot=50` вместо 150, а Bybit и MEXC стояли в `paused`.
Восстановление происходило только спустя ~минуту.

```
13:23:36 rotate: focus=50 — разбирается с подписками (десятки секунд)
13:23:55 disable() → set_focus(None) → resume() → wake.set()
13:24:32 rotate закончил, вошёл в _sleep_rotate → wake.clear() ← СИГНАЛ СТЁРТ
```

**Фикс.** Флаг сбрасывается в момент ПОТРЕБЛЕНИЯ списка (в начале ветки
фокус-режима внутри итерации), а не перед сном. Всё, что пришло после чтения
списка, гарантированно разбудит ротацию ещё раз.

## 37. Массовые отписки блокировали ротацию на 56 секунд

**Симптом.** В том же замере между «rotate применил focus=50» и следующим
«засыпаю» прошло 56 секунд — вместо доли секунды.

**Причина.** Переход со 150 подписок на 50 требовал снять ~170 подписок
(`un_watch_order_book` + `un_watch_trades` + `un_watch_ticker`), и каждый вызов
ожидался последовательно внутри цикла ротации:

```
13:23:36 DBG rotate[Binance] focus=50
13:24:32 DBG rotate[Binance] засыпаю на 45 c     ← 56 секунд на отписки
```

Замер одного `un_watch_*` у Binance — ~0.3 c (birжа подтверждает отписку по WS).

**Фикс.** `_detach_cleanup()`: задачи потоков отменяются синхронно (подписки
перестают читать данные сразу), а сами `un_watch_*` уходят в фоновую задачу и
выполняются параллельно через `asyncio.gather`. Ротация больше не ждёт биржу.

**Та же болезнь во втором месте.** `_close_streams()` (ветка «биржа на паузе»)
тоже ожидал каждую отписку последовательно. Проявление: фокус переключили на
MEXC, Binance ушёл на паузу, и его ротация залипала на ~40 c — сигнал `resume()`
приходил, пока цикл был занят отписками. Живой замер до фикса: через 15 секунд
после выключения фокуса `Binance=online(hot 50)` вместо 150. После фикса в той же
точке замера: `Binance=online(hot 150), Bybit=online(hot 150), MEXC=online(hot 150)`.

**Регрессия:** `test_mass_unwatch_does_not_block_rotation`,
`test_pause_then_resume_is_not_blocked_by_unwatch` (обе — с медленным
`_unwatch` по 50 мс: ротация обязана применить новый набор до завершения отписок).

## 38. Устаревший пересчёт отбора включал фокус заново после выключения

**Симптом.** Лог живого замера:

```
13:08:34 [фокус Binance/swap] отбор обновлён: 17 монет за 9525 мс
13:08:54 [Bybit] возобновление стримов / [MEXC] возобновление стримов
13:08:54 фокус-режим выключен - коллекторы вернулись к горячему набору
13:09:02 [Bybit] пауза: биржа вне фокуса        ← ЧЕРЕЗ 8 СЕКУНД ПОСЛЕ ВЫКЛЮЧЕНИЯ
13:09:02 [MEXC] пауза: биржа вне фокуса
13:09:02 [фокус Binance/swap] отбор обновлён: 17 монет за 13136 мс
```

**Причина.** Отбор по «дорогим» метрикам (NATR) длится секунды — нужно скачать
свечи пулу кандидатов. Пересчёт, начатый ДО `disable()`, завершался ПОСЛЕ и
вызывал `_apply()`: снова фокус-набор на Binance и снова пауза на остальных.

**Фикс.** Счётчик «поколения» параметров `_gen`:

- `update()` и `disable()` увеличивают его;
- `refresh()` запоминает поколение до работы и сверяет после каждого долгого
  шага (после добора свечей, перед `_apply`);
- при расхождении пересчёт выбрасывает `_StaleSelection` и молча завершается;
- дополнительная проверка `if not self.enabled or gen != self._gen` стоит сразу
  ПОСЛЕ взятия блокировки — на случай, если `disable()` прошёл, пока долгий
  пересчёт держал `_lock`.

Отдельно: `POST /api/focus` больше не держит соединение по 9–13 секунд —
интерактивный пересчёт ограничен бюджетом 5 c и 60 запросами свечей
(`FOCUS_CANDLE_BUDGET`, `FOCUS_OHLCV_MAX`), остаток добирают фоновые проходы,
а UI показывает «у N монет свечи ещё не загружены — отбор уточнится».

**Регрессия:** `test_disable_during_slow_refresh_is_not_overridden`,
`test_switch_exchange_during_slow_refresh`,
`test_interactive_budget_caps_first_rank`, `test_pool_expansion_respects_budget`.

## 40. Смоук-тест «сортировка по объёму убывает» падал на ВЕРНЫХ данных

**Симптом.** Проверка jsdom-смока стабильно краснела, хотя сервер отдавал строки
в правильном порядке (подтверждено `/api/screener`: `vols == sorted(vols, reverse=True)`).

**Причина.** Тест парсил текст колонки «Объём» так:

```js
parseFloat("1.24B".replace(/[^0-9.\-]/g, ""))  // → 1.24
parseFloat("950.3M".replace(/[^0-9.\-]/g, "")) // → 950.3
```

Компактный формат (`fmt.compact`) терял суффикс, и 1.24 миллиарда оказывалось
«меньше» 950 миллионов. То есть тест проверял не сортировку, а собственную
неспособность прочитать число.

**Фикс.** Парсер компактных чисел в смоке с явной таблицей множителей
`{K:1e3, M:1e6, B:1e9, T:1e12}` и выводом значений при падении.

**Мораль (вторая за проект после п.25 и п.36):** проверка, которая никогда не
срабатывает, бесполезна — но проверка, срабатывающая на верных данных, вредна:

## 41. Кнопка «сброс» не сбрасывала сортировку, поставленную пресетом

**Симптом.** Пользователь нажимает пресет «Максимальная волатильность», затем
«сброс» — фильтры очищаются, но таблица продолжает стоять в порядке NATR.
Колонка «Объём» при этом не убывает, и выглядит это как сломанная сортировка.

**Причина.** `applyPreset()` умеет применять из пресета не только диапазоны, но
и `sort`/`desc` (`state.sortCol = v`), а `resetFilters()` чистил только
`state.filters`, `state.exchanges` и поиск. Сортировка оставалась от пресета,
и `buildGridHead()` продолжал рисовать стрелку на колонке NATR.

**Как нашли.** jsdom-смоук: новая проверка фокус-режима нажимала пресет
«волатильность», а следующая за ней старая проверка «сортировка по объёму
убывает» падала — хотя до этого проходила. То есть тест поймал не свою поломку,
а чужой незакрытый след: до появления фокус-режима пресет в этом месте смока
просто не нажимали.

**Фикс.** `resetFilters()` сбрасывает `sortCol="vol"`, `sortDesc=true` и
перерисовывает шапку таблицы (стрелка сортировки снимается).

**Регрессия:** существующие проверки смока «сброс очищает фильтры» и
«сортировка по объёму убывает» теперь идут подряд после применения пресета —
именно та последовательность, на которой баг воспроизводился.

## 42. Сетка графиков показывала демо-свечи, когда сервер честно ответил «пусто»

**Симптом.** В фокус-режиме на бирже, которая не подключилась (или пока отбор

фильтр или увеличьте «монет в стриме»», в полном режиме — прежний текст про
неподключённый рынок.

«все ячейки одной биржи» идут по живому ответу `/api/grid`; отдельный смоук
`tests/smoke_focus_demo.js` проверяет DEMO-путь (там синтетика разрешена и
помечена «локальный отбор (DEMO)»).

## 44. doctor.py и лог коллектора прятали настоящую причину ExchangeNotAvailable

**Симптом.** У пользователя (Windows) все сетевые слои doctor.py зелёные
(TCP, DNS, TLS, прямые HTTPS-запросы 8/8), а шаг 5 падает на ВСЕХ биржах
мгновенно (0.3–0.4 c) с сообщением вида:

    ExchangeNotAvailable: binanceusdm GET https://fapi.binance.com/fapi/v1/exchangeInfo

— и всё. Ни SSL-ошибки, ни «connection reset», ни кода ответа. Диагноз по
такому сообщению невозможен.

**Причина.** ccxt маскирует сетевые ошибки так:

    except aiohttp.ClientConnectionError as e:
        details = ' '.join([self.id, method, url])
        raise ExchangeNotAvailable(details) from e

Настоящая причина (ClientConnectorSSLError, ServerDisconnectedError,
gaierror, отказ прокси…) уходит в `__cause__`, а `describe_error()` читал
только `str(e)` — то есть ровно тот бесполезный URL. Ошибки всех восьми
бирж выглядели одинаково.

**Фикс.** `_root_cause()` разворачивает цепочку `__cause__`/`__context__`
(с защитой от циклов) и `describe_error()` дописывает корень:

    ExchangeNotAvailable: binanceusdm GET https://… ← ConnectionRefusedError: [Errno 111] Connect call failed ('127.0.0.1', 9)

Подсказки («сертификаты», «прокси», «обрыв соединения»…) теперь ищутся по
тексту всей цепочки; добавлена ветка для «forcibly closed / connection
reset / 10054 / server disconnected». doctor.py печатает до 400 символов
вместо 150.

**Регрессия:** `tests/test_diagnostics.py` — цепочка из одного и трёх
уровней, SSL-причина с подсказкой, цикл в `__context__` (не вешается),
одиночное исключение без `←` (прежнее поведение).

## 45. «Прямые запросы проходят, а ccxt падает»: системный прокси Windows + сломанный PROXY_URL

**Симптом.** Тот же прогон: urllib-запросы (шаг 4 doctor.py) отвечают 200
за ~0.5 c, а ccxt (шаг 5) — мгновенный отказ на всех биржах. Классическая
картина «VPN включён, но скринер о нём не знает».

**Причины — три, накладывались друг на друга:**

1. **Слепое пятно диагностики.** Шаг 4 ходит через `urllib.request`, а он
   на Windows читает системный прокси из реестра (WinINET
   `ProxyEnable/ProxyServer`) — его включают VPN-приложения (Clash, v2rayN,
   Outline и т.п.). aiohttp/ccxt реестр игнорируют и идут напрямую. Doctor
   проверял только переменные окружения и рапортовал «прокси не заданы».
2. **Сломанный PROXY_URL.** `apply_proxy()` ставил ОДНОВРЕМЕННО
   `httpProxy` и `httpsProxy`, а ccxt (проверено на 4.5.85,
   `check_proxy_settings`) бросает на эту комбинацию
   `InvalidProxySettings: multiple conflicting proxy settings` — то есть
   главный совет doctor.py («задайте PROXY_URL») ломал вообще все биржи.
   Правильная схема: REST — ровно один `httpsProxy` (ccxt передаёт его в
   aiohttp `proxy=`), WebSocket — `wssProxy` (ccxt читает WS-прокси
   отдельной группой `wsProxy/wssProxy/wsSocksProxy` через
   `check_ws_proxy_settings()`).
3. **Шаг 5 doctor.py игнорировал PROXY_URL**: `SETTINGS_PROXY_OVERRIDE`
   выставляется из настроек только в `app/api.py`, поэтому doctor проверял
   прямой выход даже при настроенном прокси и давал ложный FAIL.

**Фикс.**
* `apply_proxy()`: `httpsProxy` + `wssProxy` (без `httpProxy`), плюс
  одноразовое предупреждение в лог, если PROXY_URL не задан, а системный
  прокси Windows включён (или задан PAC);
* `app/preflight.py`: `windows_system_proxy()` (реестр, безопасно на всех
  ОС) и `normalize_proxy_server()` («http=h1:p1;https=h2:p2» → URL);
* doctor.py: раздел 1 печатает версии aiohttp/yarl/multidict и состояние
  системного прокси; новый раздел **4b** гоняет один запрос через aiohttp
  четырьмя способами (certifi / системное хранилище CA / без проверки /
  через прокси) и по комбинации результатов различает «нужен PROXY_URL»,
  «TLS-перехват антивируса» и «файрвол режет python.exe»; шаг 5 применяет
  PROXY_URL как run.py; добавлены советы `proxy_split`/`tls_mitm`/
  `aiohttp_blocked` и пункт про реестр в «Общие шаги»;
* `tools/devproxy.py` — минимальный CONNECT-прокси для проверки.

**Проверено живьём в песочнице:** doctor через devproxy — шаг 5 OK
(920 рынков за 0.3 c); `watch_ticker("BTC/USDT:USDT")` через тот же прокси
— живая цена (wssProxy туннелирует WSS); с мёртвым прокси шаг 5 печатает
`← ConnectionRefusedError: Connect call failed ('127.0.0.1', 9)` вместо
голого URL.

**Регрессия:** `tests/test_diagnostics.py` — `apply_proxy` обязан давать
opts, которые проходят настоящую валидацию ccxt
(`check_proxy_settings`/`check_ws_proxy_settings` на живом объекте биржи);
`tests/test_preflight.py` — 9 форматов ProxyServer, одноразовость
предупреждения, отсутствие предупреждения при заданном прокси.

## 46. «Could not contact DNS servers»: aiodns резолвит мимо службы DNS Windows

**Симптом.** Та же машина Windows: шаги doctor 1–4 полностью зелёные
(трафик есть, DNS резолвит, urllib получает HTTP 200), а шаг 5 мгновенно
падает на всех биржах. Размотка цепочки `__cause__` (фикс #44) наконец
показала настоящую причину:

```
ExchangeNotAvailable: binanceusdm GET https://fapi.binance.com/fapi/v1/exchangeInfo
  ClientConnectorDNSError: Cannot connect to host fapi.binance.com:443 ssl:default [Could not contact DNS servers]
    OSError: [Errno None] Could not contact DNS servers
      DNSError: (11, 'Could not contact DNS servers')
```

**Причина.** `ClientConnectorDNSError` в aiohttp поднимается только из
`AsyncResolver` (connector.py, ветка aiodns). ccxt 4.5.52 тянет `aiodns`
обязательной зависимостью (проверено по метаданным PyPI; из новых версий
ccxt её убрали), и aiohttp при установленном aiodns выбирает его
резолвером по умолчанию. AsyncResolver шлёт DNS-запросы **прямым UDP к
серверам из настроек адаптера**, минуя службу DNS-клиента Windows
(dnscache). Этот путь регулярно блокируют: антивирус с веб-экраном,
файрвол с правилами по процессам, VPN в режиме per-app routing,
«шифрованный DNS» (DoH) на адаптере. Системный же `getaddrinfo` (именно
его используют браузер, urllib и шаги 1–4 doctor) продолжает работать —
отсюда раскол «всё зелёное, а ccxt красный». Прежняя гипотеза
(системный прокси, #45) не подтвердилась: прокси был ни при чём.

**Фикс.**
* `app/collector.py`: новая `apply_dns_resolver()` — подменяет
  `aiohttp.connector.DefaultResolver` на `ThreadedResolver` (тот же
  системный `getaddrinfo`, но в пуле потоков). Патч глобальный на процесс
  и применяется в `ExchangeCollector.__init__` до создания сессий, поэтому
  покрывает и REST, и WebSocket (WS ccxt ходит через ту же aiohttp-сессию
  биржи). Отключить: `DNS_RESOLVER=aiodns` в `.env`. Хостов у приложения
  десяток, ОС кэширует ответы — на производительности не сказывается;
* `describe_error()`: отдельная ветка подсказки для
  «Could not contact DNS servers»/`ClientConnectorDNSError` — стоит ПЕРЕД
  ssl-веткой, потому что в сообщении есть «ssl:default» и оно перехватывало
  бы диагноз про сертификаты; в сравниваемый текст добавлены имена типов
  исключений цепочки;
* doctor.py: раздел 1 печатает наличие aiodns и значение DNS_RESOLVER;
  новый раздел **4c** сравнивает два резолвера в лоб (системный
  `getaddrinfo` против `aiodns.DNSResolver`) и при расколе выдаёт вердикт
  `aiodns_dns_blocked` (в problems не пишется: run.py чинит сам);
  раздел **4b** после DNS-провала прямых зондов делает контрольный запрос
  через явный `ThreadedResolver` — если он проходит, DNS-строки тоже не
  попадают в problems, а вердикт `aiodns_dns_blocked` получает приоритет
  над `proxy_split`/`tls_mitm`/`aiohttp_blocked`; шаг 5 применяет
  `apply_dns_resolver()` как run.py и печатает режим; в ADVICE и «Общие
  шаги» добавлены инструкции (DNS 1.1.1.1/8.8.8.8, отключить DoH,
  разрешить python.exe UDP/53, `ipconfig /flushdns`).

**Проверено живьём в песочнице** (установлен aiodns 4.0.4): до патча
дефолт aiohttp — `AsyncResolver`; с резолвером, указывающим на
недоступный DNS-сервер, запрос падает (у пользователя — мгновенный
отказ, в песочнице с чёрной дырой — таймаут), после
`apply_dns_resolver()` тот же запрос через дефолтную сессию — HTTP 200;
ccxt `fetch_ticker` и `watch_ticker("BTC/USDT:USDT")` работают через
ThreadedResolver (живая цена); полный `python doctor.py binanceusdm`
проходит все разделы включая 4b/4c без предупреждений.

**Регрессия:** `tests/test_dns_resolver.py` — 14 тестов: дефолт/aiodns-режимы
`apply_dns_resolver`, вызов из `ExchangeCollector.__init__`, новый
коннектор реально получает ThreadedResolver, подсказка `describe_error`
для точной цепочки пользователя и её приоритет над ssl-веткой, 4c при
отсутствующем/сломанном/живом aiodns (подмена `sys.modules` и
`socket.getaddrinfo`), 4b: DNS-провал + живой контрольный зонд →
`aiodns_dns_blocked` и пустой problems, полная блокировка → по-прежнему
`aiohttp_blocked`.


## 47. «Всё ужасно тормозит»: книжный поток съедал больше ядра, а фронтенд сериализовал DOM каждую секунду

**Симптом.** Жалоба пользователя: тормозит всё сразу — таблица дёргается,
графики обновляются рывками, пуш отстаёт. Классический признак: event loop
сервера захлёбывается, и тогда отстают ВСЕ задачи (пуш, REST, алерты, WS).

**Диагностика (замер, не догадка).** Новый `tools/bench_perf.py` — офлайн-
бенчмарк на синтетике в 6000 символов (размер боевого CORE-профиля):

* `apply_book()` (полный пересчёт стакана 200+200) — **~346 мкс**: кластеризация
  плотностей 247 мкс + имбаланс 45 мкс + нормализация 41 мкс. Биржи шлют стаканы
  5–10 раз/с на символ, книг в CORE ~510 → реалистичная симуляция одной секунды
  книжного потока: **1557 мс CPU — больше полутора ядер**. Это и был главный
  потребитель: event loop не успевал отправлять пуш вовремя.
* `to_row()` × 6000 — 92 мс/с (терпимо, но `ret()` внутри делал линейный скан
  истории на каждый из 5 таймфреймов, 30 000 вызовов/с).
* `overview()` — обход всех символов на КАЖДЫЙ пуш КАЖДОМУ WS-клиенту.

Во фронтенде (ревью кода рендера):

* `renderTable`: сравнение `td.innerHTML !== html` — браузер СЕРИАЛИЗОВАЛ DOM
  каждой ячейки обратно в строку: ~2850 сериализаций/с на 150 строках; колонка
  «символ» писалась в DOM вообще безусловно; при живой сортировке каждая
  переставленная строка искалась `body.querySelector` (O(n²) обходов/с).
* `renderMap`: `host.querySelector` на каждую из 300 плиток + 5 querySelector
  внутри плитки на каждый текст — ~1800 поисков по дереву в секунду; стили
  (width/height/background) переписывались у всех плиток каждый пуш.
* `chart.js`: `updateLast()` вызывал `render()` немедленно на каждый тик —
  в сетке до 16 полных перерисовок canvas на один батч пуша, часть в один кадр.

**Фикс.**

*Сервер:*
1. `apply_book(min_interval=...)` — тяжёлая часть (кластеризация + имбаланс)
   не чаще раза в `BOOK_DENSITY_INTERVAL` (дефолт 0.25 с = 4 Гц на символ,
   глазу плотности быстрее не нужны). Лёгкая часть (нормализованный стакан,
   bid/ask) обновляется КАЖДЫЙ апдейт — лестница цен и подсветка остаются
   свежими. Дефолт 0.0 сохраняет старое поведение для replay/тестов.
2. `ret()` — бинарный поиск по `RingBuffer.bisect_ts` вместо линейного скана
   (та же семантика «первая точка не старше cutoff», O(log n)).
3. `overview(ttl)` — кэш шапки; pusher и `/api/overview` берут ttl≈период пуша.
4. `/api/perf` + фоновый `_loop_lag_monitor` — диагностика тормозов числами:
   задержка event loop (EWMA), build_rows/select/push в мс, счётчики потоков.
   Замеры пишутся в `_PERF` из build_rows/select/pusher.

*Клиент:*
5. `renderTable` — diff через JS-кэш строк (`state._cellCache`): в DOM пишутся
   только изменившиеся ячейки; строки переиспользуются через `state._rowEls`
   (Map key→tr) без querySelector; кэши удалённых строк чистятся.
6. `renderMap` — `state.mapEls` (Map key→{el, ссылки на детей, кэш значений}):
   ни одного querySelector в горячем пути, стили/тексты пишутся только при
   изменении; maxVol через цикл (spread по тысячам строк — риск стека).
7. `chart.js` — `_scheduleRender()` через `requestAnimationFrame`: данные
   мутируются сразу, отрисовка коалесцируется до одной на кадр.

**Проверка (живой замер).**
* `tools/bench_perf.py`: секунда книжного потока 510×10 Гц — **1557 → 565 мс
  CPU (2.8×)**; суммарная оценка сервера ~0.7 ядра вместо ~1.7.
* Смоук (jsdom + live replay-сервер): «ВСЁ ЗЕЛЁНОЕ», JS-ошибок нет — таблица,
  карта, графики рендерятся через новые кэши корректно.
* `/api/perf` на живом сервере: loop_lag/build_rows/select/push отдаются,
  push_count растёт (84 за прогон смоука).
* `pytest tests/ -q` — 299 passed + 1 skip (было 283).
* `python tests/audit_frontend.py` — чисто.

**Регрессия:** `tests/test_perf.py` — 16 тестов: `ret()` совпадает с линейным
эталоном на случайных историях (включая гард «история короче окна»), троттлинг
пропускает тяжёлую часть, но bid/ask/лестница свежие каждый апдейт, после
интервала пересчёт происходит, `min_interval=0` — старое поведение, кэш
`overview()` уважает TTL и не мешает свежему чтению без ttl, `/api/perf`
отдаёт все поля, `build_rows` реально пишет замер в `_PERF`.

## 48. «При фокусе подписывается на все монеты»: отбор ждал свечи, а биржа тем временем стримила весь горячий набор

**Симптом.** Жалоба пользователя: «программа при фокусе начинает подписываться
на все монеты… выбираю пресет „высокая волатильность" — пусть сначала вычислит
подходящие и только потом подпишется, а не на все и вдруг попадётся, это долго».

**Диагностика (разбор кода + замер `tools/bench_focus_select.py`).** Формально
фокус и так стримил только отобранные N монет — но между нажатием кнопки и
отбором стояла стена из трёх проблем:

1. **Подписки сужались ПОСЛЕ всего отбора.** `set_focus()` вызывался из
   `_apply()` в конце `_rank()`, а отбор по «дорогим» метрикам (NATR, r3600)
   требует свечей на пул кандидатов: сотни `fetch_ohlcv` по ~1.2 c каждый.
   Всё это время (на живом Binance — десятки секунд) выбранная биржа продолжала
   стримить полный горячий набор (top_n=300, 80 стаканов, 120 лент), остальные
   биржи тоже не ставились на паузу. Со стороны это ровно «подписалась на всё».
2. **Пул кандидатов ранжировался по объёму** — худшая прокси для волатильности:
   топ-150 по объёму это мейджоры с NATR < 1%, фильтр не набирал limit монет,
   пул расширялся 3× → 6× → 12× и в пределе качал свечи для **всех 600**
   кандидатов (замер бенча: 500 `fetch_ohlcv` на вселенной 500 символов —
   ~25 c на живой бирже). Плюс `rng` (диапазон 24ч) ошибочно числился в
   `OHLCV_FIELDS`, хотя считается из high/low тикера бесплатно, а `spike`
   свечи не создают вообще (`apply_ohlcv` спайки не пишет) — оба поля зря
   запускали добор свечей.
3. **Осцилляция в полный набор при пустом промежуточном результате.** Пока
   свечи не доехали, фильтр по NATR не проходит никто → `symbols=[]` →
   `set_focus([])` → фокус снимался вовсе и коллектор возвращался к ПОЛНОМУ
   горячему набору; через проход свечи доезжали → снова сужение. Скачки
   300→N→300 подписок каждые 15 с.
4. **Фоновый `_ohlcv_loop` опрашивал весь пул** (`pool[:top_n]` = до 300
   `fetch_ohlcv` каждую минуту) — дублируя работу пересчёта фокуса, который
   и так добирает протухшие свечи пула порциями по 60.

**Лечим.**
1. *Предварительный отбор* (`FocusManager._apply_provisional`): при включении
   фокуса/смене фильтра подписки сужаются НЕМЕДЛЕННО по тикерным данным —
   ноль запросов к бирже; прочие биржи ставятся на паузу в тот же момент.
   Точный отбор по свечам догоняет и заменяет состав (strict-ротация).
   Флаг `provisional` виден в `/api/focus`, UI пишет «предварительный отбор —
   свечи уточняют состав».
2. *Прокси-ранжирование пула* (`PROXY_SORT`): вместо объёма — диапазон 24ч для
   NATR и изменение 24ч для r*-метрик (обе из тикеров, бесплатны на всю
   вселенную); направление среза уважает `desc` («Проливы» берут пул с самых
   красных). `rng` и `spike` убраны из `OHLCV_FIELDS`.
3. *Дешёвый префильтр* (`cheap_params`): условия по полям из тикеров/bulk
   (vol_min, chg, rng, fund, oiusd, …) применяются ко всей вселенной ДО подкачки
   свечей — vol_min=500k из пресета «Максимальная волатильность» сразу отсекает
   мёртвые пары, и свечи им не заказываются.
4. *Пустой промежуточный отбор не применяется*: если фильтр не набрал монет,
   а свечи ещё добираются (`enriching`), текущий (предварительный/прошлый)
   набор подписок сохраняется. Заодно `pending` в `_ensure_candles` теперь
   считает незагрузившиеся свечи («осталось без свечей» = todo − got), а не
   только срез порции.
5. `_ohlcv_loop` в фокусе опрашивает отбор (`hot`, ≤ limit), а не пул:
   свежесть свечей пула обеспечивает сам пересчёт фокуса (`ensure_ohlcv`).

**Проверка (замер).** `tools/bench_focus_select.py`: вселенная 500 инструментов
(40 мейджоров / 310 середняков / 90 «ракет» с NATR≥1.2 / 60 мёртвых), пресет
«Максимальная волатильность» (natr_min=1.0, vol_min=500k, limit=50):

| Показатель | Старая схема | Новая схема |
|---|---|---|
| `fetch_ohlcv` до первого отбора | **500** (~25 c на живой бирже) | **150** (~7.5 c) — 3.3× меньше |
| Сужение подписок | после всего отбора | **6 мс** (предотбор, 0 запросов) |
| Финальный отбор (бенч) | 157 мс | 55 мс |
| Качество отбора | 50 лучших «ракет» | те же 50 «ракет» |

* `pytest tests/ -q` — **306 passed + 1 skip** (было 299+1).
* Смоук jsdom + replay-сервер: «ВСЁ ЗЕЛЁНОЕ», JS-ошибок нет; `/api/focus`
  отдаёт `provisional`, `/api/grid` берёт ячейки из отбора.
* `python tests/audit_frontend.py` — чисто.

**Регрессия:** 7 новых тестов в `tests/test_focus.py`: подписки сужены, пока
свечи ещё «едут» (`slow_fetch` держится на Event — `_focus_syms` уже равен
limit, чужая биржа на паузе, после добора `provisional` снят); для дешёвых
фильтров предотбор не запускается и свечи не качаются; пул ранжируется прокси
по rng, а не по объёму (первыми за свечами идут «ракеты», мейджорам свечи не
заказываются); vol_min режет пул до подкачки свечей; пустой промежуточный
отбор НЕ сбрасывает коллектор в полный горячий набор (осцилляция); отбор по
rng не заказывает свечи вовсе; `_ohlcv_batch()` в фокусе = отбор, а не пул.
Обновлены `test_needs_ohlcv_detects_expensive_metrics` (rng/spike больше не
«свечные») и `test_focus_applies_filter_not_just_volume` (эталонная выборка
/api/screener расширена до 5000 строк: прокси-пул легитимно берёт среднекапы
за пределами топ-500 по объёму).

## 49. Тысячи корутин и десятки WS-соединений на биржу: подписки переведены на батчи

**Симптом.** На каждую монету горячего набора создавалось ТРИ asyncio-задачи
(`watch_ticker` + `watch_trades` + `watch_order_book`): ~320 корутин на биржу
в полном профиле и >2500 на процесс. Хуже того, у Binance (spot и futures) и
только у них ccxt строит WS-URL из СПИСКА символов (`/public/ws/<индекс>`,
индексов 50, round-robin): поточечные подписки разводили до **50 WS-соединений
на биржу** — каждое со своим read-loop'ом, TLS-сессией и throttler'ом. На
машине пользователя (Windows, VPN/прокси) это десятки лишних туннелей и
handshake'ов; event loop переключал тысячи задач в секунду (`loop_lag_ms`
рос), а пуш и `/api/grid` отставали.

**Решение.** Батчевые подписки ccxt.pro — там, где биржа их умеет
(проверено `has`-флагами и живым зондом `tools/probe_batch_ws.py` на binance/
bybit/okx/gate/mexc/aster/hyperliquid):

| Поток | Метод | Кто умеет из CORE | Итог на биржу |
|---|---|---|---|
| стаканы | `watch_order_book_for_symbols` | binance×2, bybit×2, okx×2, aster | 1 задача на ≤100 символов |
| сделки | `watch_trades_for_symbols` | + gate×2 | то же |
| тикеры | `watch_tickers` | все | то же |

Семантика совпадает с поточечной (у binance/bybit/okx одиночные `watch_*` —
это делегаты в `*_for_symbols([symbol])`, проверено по исходникам ccxt 4.5.52
и 4.5.85): books-батч возвращает ближайший обновившийся стакан с заполненным
`book['symbol']`, trades — список сделок одного символа (`trade['symbol']`),
tickers — dict обновившихся тикеров. Поточечный путь СОХРАНЁН как запасной:
mexc/hyperliquid (нет батч-методов для стаканов/сделок), gate (нет батч-
стаканов) и любой поток, где батч стабильно отказывает (`_batch_dead` →
поточечно, с прежней логикой банов отдельных символов).

**Грабли, выловленные по drodze (все — реальными прогонами):**

1. **Bybit SPOT: «args size >10».** Сервер спота принимает не больше 10 топиков
   в одном subscribe-запросе (linear — больше, но недокументированно). Первый
   живой прогон: батчи сделок/тикеров bybit:spot умерли и корректно упали в
   поточечный режим (fallback отработал как задуман). Лечение двухслойное:
   `batch_chunk=10` в конфиге bybit + авто-уменьшение чанка вдвое на ANY
   «размерной» ошибке (`args size`, `too many`, `exceed`, …) прежде чем
   объявлять батч мёртвым.
2. **Binance: счётчики подписок ccxt текут.** URL батч-подписки строится из
   списка символов, каждому уникальному списку — свой «стрим» (индекс 0..49,
   лимит 200 подписок на индекс). ccxt ИНКРЕМЕНТИРУЕТ
   `options['numSubscriptionsByStream']` при подписке и никогда не
   декрементирует при отписке. Список меняется на каждой ротации (в фокусе —
   каждые 15 c), поэтому без возврата счётчиков примерно через ~40 пересборок
   ccxt бросил бы BadRequest «reached the limit of subscriptions by stream» и
   батчи умерли бы на ровном месте. `_release_stream_counters` возвращает
   счётчики и удаляет хэш старого списка (формат хэша сверен с исходниками
   4.5.52 и 4.5.85; если ccxt его поменяет — pop промахнётся, счётчики
   вырастут и сработает безопасный fallback).
3. **Binance: отписываться нужно ВСЕМ старым списком.** У бирж с общим URL
   (bybit/okx/gate/aster) достаточно снять только выпавшие символы —
   оставшиеся не переподписываются. У binance старый список = старое
   соединение: сняв только выпавшие, мы оставили бы дубли подписок, которые
   льют дельты в общий кэш стаканов ccxt вперемешку с новым соединением
   (конфликт nonce-проверок → бесконечные ресинки). Флаг
   `batch_full_unwatch=True` в конфиге binance/binanceusdm переключает режим.
4. **Гонка отписки и fallback'а.** Когда батч умирает и ротация поднимает
   поточечные подписки, фоновая отписка старого батч-списка могла лечь ПОСЛЕ
   новых подписок (у бирж с общим URL это те же топики) и убить их. Поэтому в
   `_apply_batch_streams` отписка мёртвого батча — синхронная (await), строго
   до поточечного спавна. Обычные пересборки отписку по-прежнему не ждут
   (урок п.36: массовые un_watch блокировали ротацию на 56 c).

**Проверка (живой прогон, `EXCHANGES=binanceusdm,bybit TOP_N=20 BOOKS=10`).**
До: bybit:spot — 40 поточечных задач trades/ticker, у binance — до 50
соединений на биржу. После: `ws_streams.batch_symbols = {book: 30, trades: 60,
tickers: 60}`, `per_symbol_tasks = 0`, `batch_dead = {}`, 0 ошибок,
`loop_lag_ms` 5–10. Фокус round-trip (POST limit=8 → подписки 8/8/8 →
DELETE → 30/60/60) без единой ошибки в логе. Счётчики живые: book_updates
~200/c на 30 книгах, trades ~290/c.

**Регрессия:** `tests/test_batch_ws.py` — 16 тестов: батч вместо поточечных
задач; отсутствие батч-методов → поточечно (mexc/hyperliquid-профиль);
чанкование; маршрутизация стаканов/сделок/тикеров по `symbol` в правильные
SymbolState; отписка только выпавших (общий URL) и всем старым списком +
возврат счётчиков (binance-профиль); промах хэша безопасен; NotSupported →
поточечный fallback; серия отказов → fallback с предварительной отпиской;
пауза гасит батчи; авто-уменьшение чанка на «args size >10»; `_refresh_top`
(heapq.nlargest) сохраняет порядок; pruning кэша свечей (см. п.50).

## 50. Раунд оптимизаций по внешнему аудиту: что взято, что отвергнуто

Пришёл сторонний анализ «точек роста» (12 пунктов). Каждый проверен по коду и
замерам; взято то, что дало измеримый эффект без риска рассинхрона UI.

**Взято (бэкенд):**

1. **Лёгкий путь `apply_book` без нормализации.** Троттлинг
   `BOOK_DENSITY_INTERVAL` экономил только тяжёлую часть (кластеризация +
   имбаланс), но КАЖДЫЙ апдейт (510 книг × 5–10 Гц) строил два списка по
   200 кортежей — миллионы аллокаций в секунду. Теперь внутри окна троттлинга
   обновляется только top-of-book (bid/ask — два `float()`), полная
   нормализация живёт на тяжёлом пути (4 Гц). Замер `tools/bench_perf.py`:
   секунда книжного потока **575 → 414 мс CPU (−28%)**; bid/ask остались
   realtime (подсветка цен), лестница drawer читается при открытии карточки —
   4 Гц ей хватает. Контракт теста `test_light_part_always_fresh` обновлён
   сознательно (+2 новых теста).
2. **Кэш `select()`** (TTL 0.5 c, ключ — query+densities+отпечаток restrict):
   несколько клиентов с одинаковым фильтром (типичный случай: две вкладки,
   таблица+карта) платят за фильтрацию/сортировку 6000 строк один раз в такт.
   Заодно pusher перестал мутировать общую `meta` (копия перед правкой).
3. **orjson (опционально)** для сериализации WS-пуша: **1.4 мс → 0.1 мс** на
   payload 150 строк (9.4×, замер в bench_perf). Нет пакета — молча stdlib
   json, поведение идентично. Добавлен в requirements.txt и OPTIONAL preflight.
4. **Pruning `_candles_cache`** — РЕАЛЬНАЯ УТЕЧКА: TTL проверялся при чтении,
   но протухшие записи не удалялись; за долгую сессию кэш рос монотонно
   (запись = до 1000 свечей ≈ 100 КБ). Теперь при >512 записей сначала
   выбрасываются протухшие, затем старейшие сверх лимита.
5. **Алерты: предрасчёт области.** `evaluate()` — O(rules × rows): 20 правил ×
   6000 строк = 120 000 проверок области в секунду. Строки один раз
   группируются по (биржа, рынок), и правило с областью смотрит только свою
   группу (поиск и по лейблу «Bybit», и по id «bybit»). Группы строятся
   только когда есть правила с областью.
6. **`_refresh_top`: `heapq.nlargest`** вместо полной сортировки (топ нужен,
   упорядоченный хвост — нет).
7. **`gc.freeze()` через 3 минуты после старта** — метаданные рынков ccxt
   (~380 МБ) и стартовая масса SymbolState уходят в постоянное поколение и
   больше не сканируются сборщиками; новые символы ротации по-прежнему
   собираются дёшево.
8. **Диагностика:** `/api/perf` += `ws_streams` (батчи/поточечные/мёртвые по
   биржам), `json_engine`, `push_payload_kb`, `select_cache_hits`;
   `tools/bench_perf.py` += профиль WS-пуша (select + json/orjson);
   `tools/probe_batch_ws.py` — живой зонд батч-методов биржи.

**Взято (фронтенд):**

9. **Прунинг `prevPrices`** — Map рос вместе с ротацией символов и никогда не
   чистился (в отличие от `_rowEls`/`_cellCache`); за сутки — десятки тысяч
   мёртвых записей.
10. **Flash-подсветка без принудительного reflow.** `void td.offsetWidth` на
   каждую мигнувшую цену форсил синхронный пересчёт layout всей таблицы (до
   150 раз в секунду на живом потоке). Теперь классы чередуются
   (`flash-up` ↔ `flash-up-2`, keyframes идентичны): разное `animation-name`
   перезапускает анимацию без чтения layout.

**Отвергнуто (с причинами):**

| Пункт анализа | Вердикт |
|---|---|
| Дельта-пуш строк вместо полного снимка | Приложение однопользовательское, пуш и так узкий (≤150 строк в фокусе, ~70 КБ/с — localhost). Цена: протокол версий/удалений/пересортировки на клиенте = рассинхрон UI (класс багов, который смоки уже ловили). Выигрыш ~80% трафика localhost не нужен |
| Компактный массивный формат строк | То же: клиентский рендер переписывать ради ~35 КБ/с по локальному интерфейсу |
| Инкрементальные счётчики `overview()` | Уже кэшируется (ttl=1 c), стоимость ~7 мс/с. Инкрементальная поддержка агрегатов при ротации/purge — источник трудноуловимых расхождений шапки |
| `STORE.all()` без копирования | `list(dict.values())` на 6000 — десятки мкс; вызовов в секунду единицы. Шум |
| Объединить `/api/symbol` + `/api/candles` | Экономит ~5 мс round-trip на localhost; candles и так грузятся параллельно рендеру карточки |
| `Cache-Control` на `/api/meta` | Запрашивается один раз при загрузке страницы |
| `ohlcv_limit` 400→300 | `apply_ohlcv` и так хранит 300; выигрыш ~25% трафика свечей при риске, что биржа вернёт меньше запрошенного и `r14400` (нужно 240+1) промахнётся |
| `history_window` 900→меньше | 900 точек = ровно окно `ret(900)`; сокращение сломало бы «15м» доходность |

**Проверка.** `pytest tests/ -q` — 327 passed + 1 skipped (было 307+1);
`tools/bench_perf.py`: сумма секундных операций 706 → 541 мс CPU (−23%),
orjson 9.4× на payload пуша; `audit_frontend.py` чисто; оба jsdom-смока
«ВСЁ ЗЕЛЁНОЕ» без JS-ошибок; живой прогон binanceusdm+bybit — 0 ошибок,
батчи на всех поддерживающих биржах (см. п.49).
